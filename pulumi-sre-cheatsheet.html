Pulumi — Senior SRE Cheatsheet

Pinned version: v3.255.0 (github.com/pulumi/pulumi, released 2026-07-28 — re-check pulumi version before relying on exact patch number). CLI invoked as pulumi <command> [flags]. Auth: pulumi login (no-arg = Pulumi Cloud SaaS backend at api.pulumi.com; pulumi login --local or pulumi login s3://<bucket> / azblob:// / gs:// / file://~ for self-managed "DIY" backends). No listening ports — the CLI is a client process, not a server; all backend traffic is outbound HTTPS.

Legend: <stack> = org/project/stack-name, <urn> = resource URN, <org>/<project>/<stack> = fully-qualified stack, <key>/<value> = config entries, <version> = provider/package/policy-pack version. Naming drift: recent Pulumi releases renamed several short verbs to full words (stack init→stack new, stack ls→stack list, stack rm→stack remove, config rm→config remove, config cp→config copy, state delete→state remove); this sheet uses current canonical names — whether the old short aliases still resolve was not independently confirmed per-command, so check pulumi <cmd> --help on your installed version. Sources consulted: pulumi.com/docs (iac/concepts, iac/cli/commands, esc, deployments, insights), github.com/pulumi/pulumi releases + issues, pulumi.com/blog, pulumi-developer-docs.readthedocs.io, CNCF landscape/project pages, GitHub star counts for ecosystem tools. Items that could not be verified against a primary source are marked ⚠ unverified.

1. Components

Control plane & coordination

Deployment engine — embedded inside the pulumi binary itself, not a separate daemon; orchestrates every plan by diffing incoming resource registrations against the last checkpoint.

Language host process — the CLI launches a per-language executor binary (pulumi-language-nodejs, pulumi-language-python, -go, -dotnet, -java) that runs your program; the embedded SDK (@pulumi/pulumi, pulumi pip package, …) intercepts resource declarations and streams them out over gRPC.

Resource Monitor (resmon) — implements the pulumirpc.ResourceMonitor gRPC service; the sole channel between the language host and the engine. Resolves default providers, dispatches Construct for remote components, marshals every RegisterResource call.

Step Generator — turns each RegisterResourceEvent/ReadResourceEvent into an executable step: URN generation → prior-state lookup by URN/aliases → import check → provider Check → policy analyzer → diff → step type (Create/Update/Same/Import/Delete/Replace).

Step Executor — a worker pool sized by --parallel (default 16) runs steps serially within a dependency chain and concurrently across independent chains; cancels the whole deployment on a hard step failure.

Resource provider protocol — gRPC/protobuf (provider.proto); core RPCs: GetSchema, Configure, CheckConfig, DiffConfig, Check, Diff, Create, Read, Update, Delete, Construct, Invoke, Call, GetPluginInfo, Cancel (newer Parameterize RPC referenced in docs for dynamically-bridged providers — full current surface ⚠ unverified against the live .proto).

Provider plugin binaries — named pulumi-resource-<name>, cached under ~/.pulumi/plugins, each a standalone OS process running its own gRPC server, one per provider per run.

Data / state plane

Checkpoint — Pulumi's state snapshot; written early and often during an operation for crash recovery. Internal JSON shape isn't formally documented — inspect via pulumi stack export.

Backends — Pulumi Cloud (default, transactional REST API, recovers cleanly from partial failures, self-hostable) or "DIY": S3, Azure Blob, GCS, S3-compatible object stores, Postgres, local filesystem (file://~), set via PULUMI_BACKEND_URL or backend.url in Pulumi.yaml.

State locking — file-based advisory lock on by default on every DIY backend (no external lock table needed, unlike Terraform's S3+DynamoDB pattern); Pulumi Cloud does server-side transactional locking instead. A crashed process leaves an orphaned lock — pulumi cancel clears it without rolling back partial work.

History & versioning — Pulumi Cloud records every checkpoint transactionally, browsable in-console; DIY backends keep a checkpoint history path in the same backend storage. pulumi stack export --version <n> pulls a specific historical checkpoint.

Secrets provider — pluggable per-stack encryption set at pulumi stack init --secrets-provider=…: default (Cloud-managed), passphrase (PULUMI_CONFIG_PASSPHRASE), awskms://, azurekeyvault://, gcpkms://, hashivault://. Swap later with pulumi stack change-secrets-provider — this re-encrypts, it does not recover state you can no longer decrypt.

Stack references — new pulumi.StackReference("org/project/stack") reads another stack's exported outputs via getOutput()/requireOutput(); no automatic cross-stack deploy ordering exists — it's a read, not a trigger.

Placement, diff & routing state

Diff algorithm — the engine calls the provider's Diff RPC, which returns property-level diffs and flags each changed input as in-place-safe or replacement-required, based on the provider's own knowledge of the cloud API's immutable fields.

Replace ordering — default is create-before-replace (new resource stood up before the old is torn down, minimizing downtime); deleteBeforeReplace: true flips it to delete-then-create for resources that can't coexist (unique names, scarce IPs) — this cascades to dependents, so scope it narrowly.

Escape hatches — ignoreChanges (suppress diff on input paths — also hides real drift on those fields from preview), replaceOnChanges (force replace on paths the provider wouldn't otherwise flag, notably needed for Kubernetes CRDs where the K8s provider can't know per-CRD immutability), customTimeouts (per-resource CRUD timeout override).

URNs — every resource's state key is a URN built from type token + logical name + parent chain, not the cloud provider's own ID. aliases lists prior URNs so a rename/reparent/retype isn't read as delete+create.

Dependency graph — implicit, built from Output references passed between resources (data flow = dependency edges), plus explicit dependsOn for orderings Pulumi can't otherwise see; deletion order is a reverse topological sort decomposed into parallel-safe "antichains."

Protection flags — protect: true refuses any delete of the resource until explicitly unset; retainOnDelete: true drops the resource from state without ever calling the provider's Delete, orphaning the real object on purpose.

Runtime resource internals

Parallelism — --parallel (default 16, --parallel 1 serializes) bounds the step executor's worker pool; every provider plugin is a separate OS process, so cloud-side rate limits (not Pulumi itself) are usually the real ceiling on large stacks.

Automation API — a per-language SDK subpackage (TS/JS, Python, Go, C#, Java) that drives the same engine programmatically, no pulumi shell-out. LocalWorkspace (on-disk Pulumi.yaml) or inline programs (a function literal, no on-disk project); a WorkspaceStack exposes up()/preview()/refresh()/destroy()/outputs(). Cross-language driving is supported (a Go automation program can drive a Python Pulumi program).

CrossGuard (policy engine) — Policy Packs (TS/JS/Python or OPA/Rego) run inside the step generator's analyzer stage during both preview and up; enforcement levels advisory/mandatory/remediate; pre-built compliance packs (CIS, PCI-DSS, HITRUST, NIST) ship for the Cloud/Enterprise tier with no custom code.

Pulumi ESC — unit is the environment: a named, versioned YAML doc combining static values, secrets, dynamic values pulled from AWS Secrets Manager/Vault/Azure Key Vault/1Password, OIDC-minted per-cloud short-lived credentials, and values composed from other environments. Standalone esc CLI is being folded into the main pulumi CLI's env subcommand (active transition as of mid-2026 — confirm current split before scripting against it).

Ingest, storage substrate & recovery

Import — pulumi import (CLI-first) generates the resource declaration and writes state without ever calling the provider's Create; requires declared inputs to exactly match live state or it hard-fails. CLI-first auto-protects the imported resource; code-first/bulk import (pulumi preview --import-file) does not — add protect: true yourself.

Backup/restore surgery — pulumi stack export [--file f.json] → hand-edit a copy → pulumi stack import --file f.json --force; state must stay in dependency order or the reimport is corrupt even though it's valid JSON. Prefer dedicated pulumi state subcommands over raw JSON edits wherever one exists.

Drift reconciliation — Pulumi does not implicitly refresh before every operation (deliberate, for performance/predictability); pulumi refresh reconciles recorded state against real cloud state, pulumi up --refresh bundles refresh+update, and options.refresh: always in Pulumi.yaml makes refresh the default for that project.

Restoring a deleted/corrupted stack — pulumi stack history to find a good prior update, pulumi stack export --version <n> to pull that checkpoint, then pulumi stack import to restore it; Pulumi Cloud also offers a "restore deleted stack" console action. DIY-backend backup mechanics beyond the checkpoint history path are ⚠ unverified — pair with your own bucket versioning as a safety net.

Lifecycle & platform services

Config precedence — per-stack values live in Pulumi.<stack>.yaml (project defaults in Pulumi.yaml); when a key is set both by an imported ESC environment and explicit stack config, the explicit stack config wins (documented precedence rule). ESC values project either as process env vars or directly as pulumiConfig keys.

Pulumi Cloud services — Search (cross-cloud resource search from one pane), Deployments (managed, isolated remote execution of preview/up, PR-comment previews, scheduled drift jobs), Insights (governance/policy extended to resources discovered outside Pulumi-managed IaC across AWS/Azure/OCI/Kubernetes), RBAC/Teams/Orgs (Teams-based access to stacks/environments/Insights — gated to Enterprise/Business Critical tiers).

Provider SDK for custom providers — official template is pulumi/pulumi-provider-boilerplate (native provider, CustomResource + ComponentResource examples) built on the Pulumi Go Provider SDK (pulumi-go-provider), which derives schema from Go type reflection instead of hand-written JSON; a separate pulumi-tf-provider-boilerplate exists for Terraform-bridged providers.

Automation API

What it is — a per-language SDK (TS/JS, Python, Go, C#, Java) that drives the same engine as the CLI programmatically: LocalWorkspace/RemoteWorkspace plus a Stack object exposing up(), preview(), refresh(), destroy(), outputs().

Where a senior reaches for it — self-service internal developer platforms, multi-tenant SaaS provisioning (per-customer stacks), Backstage-style portals, custom REST/gRPC infra APIs, integration test harnesses (spin up → assert → destroy), and CI orchestration needing real error handling around preview/up instead of shell exit codes.

4. Top Incidents

Walk any incident out loud: observe the actual error/diff first, not the ticket's paraphrase → localize: is this control-plane (the engine/state/lock) or data-plane (a real cloud resource the provider touched)? → let pulumi preview --diff / stack export / provider error text name the cause instead of guessing → stabilize (unblock the stack — cancel a lock, refresh drift) before you fix (correct the code/config) → name the prevention so it doesn't recur.

1. Stuck/abandoned state lock

Symptom: error: [409] Conflict: Another update is currently in progress (Pulumi Cloud) or a lock-file error (DIY backend); every subsequent up/preview/destroy on the stack fails immediately.

Root cause: a CLI process was SIGKILLed, OOM-killed, or its spot instance was reclaimed mid-update, leaving an active lease (Cloud) or lock object at .pulumi/locks/<stack>/$lock.json-style path (DIY) with no process left to release it.

Fix: confirm no one is genuinely mid-update (check the Cloud console for the latest update's initiator), then pulumi cancel; a [400] the update has already completed response is safe to ignore. Follow with pulumi refresh --clear-pending-creates to clean up anything left mid-flight. Prevent: set CI job timeouts with a cleanup step that runs pulumi cancel --yes on failure/kill.

2. State drift causing unexpected diffs/replaces

Symptom: preview/up proposes changes or replacements nobody made in code.

Root cause: Pulumi does not implicitly refresh before every operation (deliberate, for speed/predictability) — console click-ops or another tool's out-of-band change goes unnoticed until someone runs refresh.

Fix: pulumi refresh then preview --diff to review before applying, or pulumi up --refresh to bundle both. Prevent: set options.refresh: always in Pulumi.yaml, or a scheduled pulumi refresh --preview-only --expect-no-changes CI job that fails loudly on any drift.

3. Accidental delete+create from a rename or immutable property

Symptom: a variable rename, reparent, or trivial property edit shows - delete + + create for a resource that should be untouched (databases are the classic victim).

Root cause: a resource's identity is its URN (name+type+parent+project+stack); changing any of those changes the URN and the default behavior is delete-old/create-new. Some cloud properties are also provider-declared immutable, forcing a replace independent of naming.

Fix: add the old URN to aliases on the renamed/moved resource and confirm with preview that it now shows an in-place update, not delete+create. Prevent: require preview --diff in CI before any rename/refactor merges; set protect: true on stateful/critical resources.

4. Secrets provider misconfiguration / lost KMS access

Symptom: AccessDenied on kms:Decrypt when reading encrypted config/state; team fully locked out of decrypting existing state.

Root cause: the calling identity lacks kms:Decrypt in IAM and/or the KMS key policy; if the key itself is deleted/disabled, anything encrypted with it is unrecoverable.

Fix: repair IAM + key policy grants; if the old key is truly gone, pulumi stack change-secrets-provider only helps if you can still decrypt with the old key first — it re-encrypts forward, it does not recover from an unreadable key. Prevent: validate KMS encrypt/decrypt grants during environment bootstrap; treat key deletion protection/rotation as part of your state DR plan.

5. Provider version bump causing broad diffs across the stack

Symptom: upgrading a provider package produces diffs across nearly every resource of that type, or unexpected forced replacements with no real-world change.

Root cause: bridged providers periodically make breaking schema changes tracking their upstream Terraform provider; if program code isn't updated in lockstep, Pulumi sees the old input shape vs. the new provider's expected shape as a diff.

Fix: read the provider's changelog before a major bump; update input shapes to match; preview --diff to confirm no unintended replaces; pin with pulumi plugin install resource <name> <version> if a version-mismatch warning appears. Prevent: bump provider majors deliberately, isolated from other changes, on a low-risk stack first; assert expected plugin versions in CI via pulumi plugin list.

6. Corrupted or manually-edited state

Symptom: up fails schema/parse validation after a hand-edited stack export is reimported, or after an I/O error mid-write during a network partition.

Root cause: state is an ordered document — dependent resources must appear after what they depend on — and manual edits that break ordering or drop a dependency edge corrupt it even though the JSON itself is well-formed.

Fix: try, in order: pulumi refresh; upgrade the CLI; use pulumi import instead of hand-editing for resources that already exist in the cloud; as a last resort, back up the export, edit a separate copy, then stack import. Prefer pulumi state subcommands over raw JSON surgery. Prevent: never let two people edit an export/import cycle concurrently — no lock protects that window.

7. Parallelism-driven cloud API rate-limiting

Symptom: large stacks with high --parallel hit provider-side throttling — e.g. Kubernetes client "throttling request" warnings, or intermittent bulk-create failures.

Root cause: Pulumi's default parallelism can exceed a provider's own client throttle (K8s client-go defaults to QPS 5 / Burst 10) or the cloud API's own rate limit, independent of Pulumi.

Fix: lower --parallel/PULUMI_PARALLEL for the affected stack; for Kubernetes specifically, raise client QPS/Burst via provider env vars ⚠ sourced from a GitHub issue thread only, not an official docs page — verify the exact var names before scripting. Prevent: tune parallelism per-stack against empirically observed limits rather than leaving very large stacks on defaults.

8. Concurrent applies on a non-Cloud (DIY) backend

Symptom: two pipelines (or a human + CI) run up on the same stack simultaneously against S3/Blob/GCS, producing a corrupted or clobbered checkpoint.

Root cause: DIY backends do implement file-based locking by default (contrary to older assumptions of "no concurrency control"), but Pulumi itself describes it as "basic" — historically and in edge cases, concurrent writes could still race.

Fix: restore from the backend's timestamped checkpoint backup (or your own bucket versioning), then pulumi refresh. Prevent: never let CI pipelines run overlapping up/destroy for the same stack — serialize deploy jobs; enable bucket versioning on the DIY backend's storage as a safety net; consider Pulumi Cloud's server-side locking for teams with real concurrent-deploy risk.

9. Import failures on existing infrastructure

Symptom: pulumi import fails with "inputs to import do not match the existing resource" — often from subtle casing/default-value mismatches; bulk program-first imports fail across many resources at once.

Root cause: import requires the program's declared inputs to exactly match the live resource's reported state; any mismatch (casing, defaulted/computed fields you didn't specify) is a hard failure, not a partial import.

Fix: iterate on input values using the mismatch warnings; CLI-first import emits generated code you can copy in directly. For many resources, use pulumi preview --import-file to generate a manifest to review before executing. Prevent: prefer CLI-first import for a handful of resources (it auto-protects), review the generated import manifest carefully for bulk imports.

10. Cross-stack reference breakage

Symptom: a downstream stack's preview/up fails or silently computes a wrong value after an upstream team renames or removes a stack output the downstream StackReference reads.

Root cause: requireOutput() fails at deployment time only, with no compile-time contract between stacks — there is no automatic ordering or notification when an upstream stack's output shape changes.

Fix: use requireOutput (fails loudly, easy to diagnose) rather than an optional getOutput for mandatory values; use getOutputDetails to inspect a referenced output directly while debugging. Prevent: treat stack outputs as a versioned interface between teams — communicate before renaming/removing a consumed output; consider Pulumi ESC for shared values instead of chaining ad hoc stack references.

5. Core Concepts & Tradeoffs

ConceptHow it works & the tradeoff
Declarative vs. imperative authoringBoth Pulumi and Terraform/OpenTofu are declarative execution models — you describe end state, the engine computes the diff. Pulumi's authoring layer is a general-purpose language (loops, conditionals, real package managers, IDE tooling) instead of HCL. Tradeoff: GP-language expressiveness and reuse vs. HCL's more constrained, more uniformly-analyzable surface (easier static tooling, more predictable plan output across a large team).
Reconciliation modelEngine diffs desired (program-evaluated) state against last-recorded state, computes CRUD ops. Neither Pulumi nor Terraform auto-rolls-back a failed apply — both leave infra partially updated for the operator to reconcile forward (re-run, or revert+re-run).
State as source of truthThe checkpoint, not the cloud, is what Pulumi believes exists — which is why drift matters. pulumi refresh --preview-only diffs recorded vs. live state without mutating either; refresh is deliberately not automatic before every op (performance/predictability tradeoff), so silent drift is the cost of not running it on a schedule.
Diff/replace decision treeThe provider's own Diff RPC is authoritative on update-in-place vs. replace, based on which cloud fields are immutable. Escape hatches trade blast-radius for control: ignoreChanges (suppress a diff, but also hides real drift there), replaceOnChanges (force a replace the provider wouldn't otherwise flag — needed for K8s CRDs), deleteBeforeReplace (flip ordering, cascades to dependents).
Concurrency/lockingDIY backends: cheap file-based advisory locks, no extra infra, but blunt — whole-stack exclusive, manual cancel needed after a crash. Pulumi Cloud: transactional server-side locking, no external lock table needed (unlike Terraform's typical S3+DynamoDB pattern) — trades self-hosting simplicity for a SaaS/managed-service dependency.
Secrets handlingSecret values are encrypted in state by default, per-stack, pluggable KMS backend. Passphrase mode trades convenience for a shared-secret-distribution problem across a team/CI; cloud KMS trades setup complexity for centralized rotation/audit. Contrast: Terraform's default state has sensitive values unencrypted at rest unless an external layer (e.g. Vault) is bolted on.
Multi-language supportProvider SDKs are codegen'd from one schema (the provider's GetSchema RPC response) into per-language bindings — one schema author, N language packages, vs. Terraform's HCL-only provider surface needing separate community bridges into other ecosystems. Tradeoff: the provider author now owns a codegen/release pipeline per target language, and generated-SDK quality varies by language.
Component vs. custom resourcesA CustomResource maps 1:1 to a provider-managed cloud object with real CRUD. A ComponentResource is a graph node with no CRUD of its own — pure encapsulation/reuse, provisioned by creating its children. Unlike Terraform modules (which the docs describe as static HCL units that flatten into state), components are real, addressable graph nodes — reusable "infra modules" at the cost of an extra layer to reason about when debugging dependency/graph issues.
Stack-per-environment vs. single-stackStandard pattern is one stack per environment (dev/staging/prod), each with independent config/secrets and blast-radius isolation — at the cost of keeping N stacks' code and cadence in sync, mitigated by stack references and/or component reuse.

6. System Design & Capacity Planning

LeverRule of thumb / guidance
Stack structuring spectrumThree named patterns from Pulumi's own guidance: Monolithic (one stack per environment, everything together — simplest, but one blast radius and one permission boundary); Layered (split by infra layer — network → cluster → workload — wired via stack references; "the recommended default once a monolith starts to hurt"); Micro-stacks (one stack per service — max isolation, highest coordination overhead, warranted only for genuinely independent services). No single prescribed projects-to-stacks ratio.
Stack-reference blast radiusLayering reduces per-deploy blast radius (deploy only the changed layer) at the cost of cross-stack coordination — a downstream layer can read a stale upstream output if the two aren't deployed in the right order; layered/micro-stack patterns need an explicit deploy-ordering mechanism, since Pulumi provides none automatically.
CI/CD shapePreview-then-apply gating is standard: preview as a required PR check, up gated behind branch-protected merge/manual approval. Pulumi Deployments (Cloud/Enterprise) runs these in an isolated managed environment instead of a self-hosted runner. Drift detection is a separate scheduled job (refresh --preview-only --expect-no-changes, or the Cloud-native scheduled Drift feature). up --diff renders the rich diff for human review during apply.
State backend choice at scaleDIY (S3/Blob/GCS) avoids SaaS dependency and per-seat cost but pushes locking, history, RBAC, and secrets-provider key management entirely onto the platform team. Pulumi Cloud (or self-hosted Pulumi Cloud) centralizes all of it as a managed service — tradeoff is SaaS dependency (or shifted-but-retained operational burden if self-hosted) vs. DIY's lower-level, roll-your-own operability.
RBAC/team scalingTeams-based RBAC is unified across stacks, ESC environments, and Insights in one control plane, but Teams is gated to Enterprise/Business Critical tiers — a real procurement input for large orgs planning fine-grained org-scale access control.
Multi-region / DRNo built-in multi-region primitive — region is just a provider config value per stack; DR pattern is deploying the same program against a second region's stack, or a component that provisions both. Backup is the state backend's own versioning (S3/GCS/Blob object versioning, or Pulumi Cloud's built-in checkpoint history) — there is no separate "Pulumi backup" product.
When NOT to use Pulumi(reasoned from Pulumi's own comparison docs, not a verbatim vendor statement) — vs. Terraform/OpenTofu: an org standardized on HCL-only tooling (Sentinel, module registries, existing HCL codebase) gains little from adding a language-runtime dependency to every CI runner. vs. AWS CDK/CloudFormation: an AWS-only shop already invested in StackSets/Change Sets may prefer CloudFormation's automatic rollback-on-failure semantics over Pulumi's scriptable-but-manual-reconciliation model. vs. raw CloudFormation: small, single-account, single-team, AWS-only footprints that want zero external state-backend to operate are better served staying cloud-native, at the cost of single-cloud lock-in.

7. Q&A — Rapid-Fire Talking Points

Pulumi vs. Terraform, the core difference? — Both are declarative execution engines under the hood; the difference is the authoring layer — general-purpose languages (loops, classes, package managers) vs. Terraform's HCL DSL.

How does Pulumi get multi-language support? — Providers are gRPC services driven by a schema describing resources/inputs/outputs; codegen turns that one schema into per-language SDKs. Not N native reimplementations per provider.

Provider vs. resource? — A provider is the plugin (gRPC binary) implementing Configure/Diff/Create/Update/Delete/GetSchema for a platform; a resource is a single managed object the provider knows how to CRUD.

Why does state matter, and what if you lose it? — State correlates code to real cloud IDs, which is what makes up a diff instead of blind recreation. Losing it means no automatic recovery of destroyed resources — recover via a backup export/import, Pulumi Cloud's restore-deleted-stack, or manual re-import of every resource. DIY backends get zero automatic recovery; you own backup/versioning.

How do you avoid drift? — Scheduled pulumi refresh --preview-only --expect-no-changes (CI cron or Pulumi Deployments' Drift trigger); Cloud can optionally auto-remediate with up --refresh when drift is found.

What forces replacement vs. in-place update? — Provider-defined: an input flagged immutable in the provider's Diff forces replace. Default ordering is create-before-replace (minimizes downtime); deleteBeforeReplace flips it for resources that can't coexist.

Stack references and their limitation? — StackReference reads another stack's outputs but triggers nothing — Pulumi does not automatically order or cascade cross-stack deploys; teams bolt on ordering via CI pipeline stages.

Is pulumi up idempotent? — By design, yes, for a deterministic program with no code/config changes it's a no-op re-run. Not universally guaranteed — depends on program determinism; one-shot operations like import are not idempotent.

How do secrets work? — Config values marked --secret are encrypted per-value at rest under a pluggable backend (Cloud default, local passphrase, or cloud KMS/Vault via provider URL scheme).

Pulumi ESC vs. plain stack config? — ESC is a centralized, composable config/secrets service that can pull dynamically from Secrets Manager/Vault/1Password and mint short-lived OIDC cloud credentials, feeding stack config or env vars; explicit stack config still wins over ESC on a key conflict.

How do you do zero-downtime changes? — Default create-before-delete replacement, protect: true to block accidental deletes; blue-green (parallel services/target groups) is hand-rolled in Pulumi code, not a built-in primitive.

How do you test Pulumi code? — Three tiers: unit tests with in-process mocks replacing provider gRPC calls (native test framework, no cloud creds, milliseconds); policy packs/property tests seeing real input/output values during preview/up; integration tests that deploy-verify-destroy against real cloud.

Automation API use cases? — Self-service internal platforms, multi-tenant SaaS provisioning, Backstage-style developer portals, custom infra APIs — anywhere you want up/preview/destroy called from your own app instead of shelling out.

Where does CrossGuard actually enforce? — Both preview (batches all violations into a report) and up (halts on the first mandatory violation before that resource touches the cloud) — genuinely pre-apply, per-resource, not a post-hoc scan.

8. Lesser-Known Facts & Pro Tips

Fact / knobWhy it's useful
retainOnDelete: trueSkips the provider's Delete call entirely — the cloud resource survives, only Pulumi's record of it goes away. Different from protect: use it to deliberately hand a resource off to be managed another way.
deleteBeforeReplace: trueCascades to dependent resources, which can add real downtime — apply narrowly to the specific resource that needs it, not globally.
additionalSecretOutputsCustom-resource-only; augments (doesn't replace) Pulumi's automatic secret-inference — marks an output secret that Pulumi wouldn't otherwise infer, e.g. a generated password a provider returns that isn't itself a secret input.
Secret propagation is transitive but the plaintext still reaches your codeCombining a secret Output via .apply/Output.all marks the result secret too and keeps it out of state — but the apply callback body receives the plaintext, so a stray console.log inside it still leaks the secret to logs. Pulumi can't police the callback body.
Config secrets are per-stack, not sharedconfig set --secret encrypts under that specific stack's key — there's no built-in way to share a secret across stacks/projects except Pulumi ESC.
options.refresh: always in Pulumi.yamlForces a refresh before every preview/update/destroy for that project — opt-in, because implicit refresh isn't the default (performance/predictability tradeoff). As of v3.160.0, --run-program on refresh/destroy additionally re-runs your program during those ops (opt-in now, planned default later) — known to interact badly with retainOnDelete in a snapshot-integrity edge case, avoid combining until confirmed fixed on your version.
CLI-first vs. code-first importCLI-first auto-sets protect: true on the imported resource; code-first/bulk import via preview --import-file does not — add the protect option yourself or a freshly-imported prod resource is one careless destroy away from deletion.
pulumi destroy has no default scopingIt destroys the whole stack. Always reach for -t/--exclude for partial operations; the safe teardown sequence is destroy → confirm empty → stack remove (without --force, which refuses if resources remain — that refusal is your safety net, don't route around it casually).
dependsOn vs. implicit dependenciesPulumi infers ordering automatically whenever one resource's Output feeds another's input — that's the default and preferred path. Reach for explicit dependsOn only for orderings Pulumi can't see (IAM propagation delay, a non-Pulumi-tracked dependency); overusing it needlessly serializes deploys that could run in parallel.
Every CLI flag has an env-var equivalent (v3.208.0+)PULUMI_OPTION_<SNAKE_CASE_FLAG> (e.g. PULUMI_OPTION_VERBOSE=9, PULUMI_OPTION_PARALLEL=4) — the fix for CI systems that can't easily inject extra CLI args per step.

Pin plugin versions in CI — assert expected provider versions with pulumi plugin list before a deploy job runs; a silent minor-version drift is a common source of "why did this diff appear out of nowhere."

Treat replaceOnChanges as a K8s-provider escape hatch first — it exists specifically because the generic Kubernetes provider can't know which fields a given CRD treats as immutable; reach for it there before assuming you need it elsewhere.

Use requireOutput, not getOutput, for anything mandatory — a missing required upstream output should fail the deploy loudly in CI, not silently propagate undefined.
